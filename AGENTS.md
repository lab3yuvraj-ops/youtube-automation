# YouTube Automation operating rules

When the user supplies a video title, run `node start-video.mjs --title "TITLE"` from the repository root on Mac, Windows or Linux. Resume an existing project with `node start-video.mjs --project "/absolute/path/pipeline.json"`; never create a replacement project for a failed step. PowerShell is not required. Install the existing Node/Python dependencies when missing. The scripting stage must retain the literal templates in `scripting/prompts/`, produce a one-minute Hindi folk-horror story with exactly 12 scenes, and preserve the reference style: flat, semi-realistic 2D Indian animation with natural adult human proportions. Use `OPENAI_API_KEY` when available; otherwise use `GROQ_API_KEY`. Never store either key in the repository.

Run Google Flow only through the authenticated persistent local Chrome profile. Create characters, backgrounds, then scenes; download every completed scene. Never require or assume six-second clips: Flow determines the natural duration required for each action and spoken line.

For every non-character-speaking scene, generate the matching Hindi narrator audio in Google AI Studio. Try Run twice. If no audio is produced, pause and say exactly: **“Hey, when I open Google AI Studio, just click on the Run button so I can proceed.”** Never continue a silent scene if narration is expected.

The full-run command generates and downloads narration and Flow clips, downloads the music, mixes audio, and renders intro/logo automatically. Do not tell the user to generate narration, download clips, or execute finishing commands manually. If a browser selector changes, inspect the authenticated page through the available browser skill, recover the specific existing generation, and continue from its saved state. Never click Generate to recover a completed or queued item, click an unrelated project-wide Download, bypass Google's verification, or assume an old queue message is the current state. For submissions made by an older local runner without a media reference, identify the matching scene in the browser before recovering it; do not select the first unrelated video in the gallery.

To recover an old completed Flow result, verify its scene and prompt in the browser, then save an ignored local JSON in `production/outputs` containing `project_file`, `scene_number`, `flow_url` and the exact `media_source` from that scene's video DOM. Run `npm run recover-scene -- --reference /absolute/path/reference.json` in production, then resume the Node workflow. Do this yourself instead of asking the student to download the result. Never print signed URLs or manufacture the reference. If the matching result cannot be identified, explain that specific blocker rather than guessing.

When the workflow emits `video_ready`, read `delivery.json`, verify the MP4 exists, and embed its `chat_markdown` in the chat response with an absolute local path. The final MP4 is already saved locally; never ask the user to download it from Flow. The CLI itself cannot write to a Codex chat, so the calling agent must deliver the file. Show the video before asking the one approval question. An existing user's individual commands and Windows PowerShell launcher remain supported.

Edit clips in scene order. Preserve full character dialogue, trim only unused narrator padding, use brief fade transitions, retain Flow character audio on character-speaking scenes, and add a premium fade/pop title only over scene 1. On non-character scenes, use the Google AI Studio Hindi narrator file, keep any useful scene ambience/SFX quietly beneath it, and never leave a silent gap. Normalize the continuous horror music bed to -20.9 LUFS. Process narrator tracks with the tested compressor/limiter chain for approximately -14 LUFS; never target 0 LUFS because it is a full-scale clipping level, not a safe spoken-audio loudness target. Use the permanent lower-right brand placement: at 1280x720, 76px high, 72px inset from the right, 75px inset from the bottom. Do not store or commit API keys, browser profiles, downloaded media, project outputs, private intro/logo files, or `.env` files.

After the final title render, record an `awaiting_approval` review state and ask one question: **“Is this video good enough to upload to YouTube?”** Show the final video, destination account and visibility. Approval authorizes automatic upload through Zernio without a second confirmation. Rejection does not upload. Collect the API key and connected YouTube account ID through local setup, never in chat. Use `review approve` or `review prompt`. Never bypass review or resubmit a project with a submission marker.

When a user says **“onboarding”**, respond exactly: **“Welcome to YouTube Automation! Please provide your channel logo image (PNG or JPG) and intro video (MP4, at least 5 seconds long, with audio).”** If the assets are already configured, acknowledge them instead of asking again. The onboarding response must ask only for these two assets. Read all other configuration from `scripting/.env`; do not ask for API keys in the onboarding response or in chat. Store supplied assets locally at the configured paths. Git itself does not execute this message; the agent delivers it when the user says “onboarding,” and `npm run setup` shows it when setup is incomplete.

When the user explicitly asks to get Freesound credentials through their connected Chrome browser or a specified Google Sheet, or says **“get all the attention”** in that context, follow `docs/freesound-onboarding.md`. Treat it as authorization for every routine setup step: navigating the connected browser, reading existing credential values, filling registration details, starting the OAuth flow, copying credentials into the local `.env`, exchanging an authorization code, validating it, and saving rotated refresh tokens. Do not ask repetitive approval questions. Pause only when the user must personally accept a legally binding Freesound API agreement or confirm creation of persistent security credentials; explain the exact single action needed, then resume automatically after it is complete. Never expose credentials in replies, logs, screenshots shared with others, or Git.
